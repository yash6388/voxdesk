# 07 — A2A: Specialist Agents as Independent Services

> Phase 3. The knowledge and booking capabilities became **independent agent services** that the
> supervisor discovers and delegates to over the **A2A (Agent-to-Agent) protocol**.

---

## 1. Plain English first

Before Phase 3, one LangGraph graph inside the API did everything. Now there are three agents:

| Agent | Where | Job |
|---|---|---|
| **Supervisor** | inside the API (FastAPI) | owns the conversation: memory, routing, small talk, confirmation UI |
| **Knowledge Agent** | own service, port 8101 | answers questions from the business's documents (RAG) |
| **Booking Agent** | own service, port 8102 | books / reschedules / cancels via the MCP server, asks for confirmation |

The supervisor doesn't import their code — it talks to them over HTTP using A2A, the same way it
would talk to an agent built by another team, in another language, on another framework.

```
Browser ─SSE─► FastAPI · Supervisor ── A2A ──► Knowledge Agent :8101 ──► Postgres (pgvector)
                    │                 └─ A2A ──► Booking Agent   :8102 ──MCP──► MCP server :8001 ──► Postgres
                    └─ small talk answered locally
```

## 1b. First: what "multi-agent" actually means (common confusion)

**Multi-agent is a design pattern, not a deployment model.** An *agent* = an LLM + its own
instructions + its own tools + a loop where it decides what to do next. *Multi-agent* = splitting a
big job across several specialised agents that hand work to each other.

*Where* those agents run is a separate decision:

| | In-process (most common) | Distributed (separate services) |
|---|---|---|
| What it looks like | One app; each agent is a LangGraph node/subgraph (or a CrewAI/AutoGen agent) passing state | Each agent is its own service; they talk over the network (A2A) |
| Pros | Simple, fast, easy to debug, shared state | Independent scaling/deploys, failure isolation, separate permissions, cross-team & cross-vendor |
| Cons | One deployable; everything scales together | Network latency, more ops, distributed debugging |
| When | Default choice for one team / one product | Different teams own agents, different scaling or security needs, agents from other frameworks or companies |

**VoxDesk shows both:**
- *In-process:* the booking agent's LangGraph loop (`booking_agent ⇄ tools → confirm`), and the
  supervisor graph routing between specialists. Before Phase 3, VoxDesk was already multi-agent this way.
- *Distributed:* Phase 3 moved the specialists into separate A2A services to demonstrate how
  cross-team / cross-vendor agents collaborate.

**Common multi-agent patterns**

| Pattern | How it works | In VoxDesk |
|---|---|---|
| Supervisor / router | One agent decides who handles each request | ✅ supervisor |
| Handoff / swarm | Agents pass control directly to one another | – |
| Hierarchical | Supervisors of supervisors | – |
| Sequential pipeline | A → B → C, each refining the output | – |

**Say it like this:**
> "Multi-agent is a design pattern — specialised agents with their own prompts and tools,
> coordinated by something like a supervisor. Usually that lives in one process, e.g. as LangGraph
> nodes or subgraphs. Distributing agents as separate services is a deployment decision, worth it
> when agents are owned by different teams, scale differently, need separate permissions, or come
> from different vendors — which is what A2A standardises. In VoxDesk I did both."

**Trap question — "Would you always split agents into services?"**
> "No. Start in-process; split only when there's a concrete reason — team ownership, scaling,
> security boundaries or interoperability — because every network hop adds latency and operational
> cost."

## 2. What A2A is

**A2A (Agent2Agent)** is an open protocol (started by Google, now under the Linux Foundation) for
agents to discover each other and collaborate on tasks.

| Concept | Meaning | In VoxDesk |
|---|---|---|
| **Agent Card** | Public JSON at `/.well-known/agent-card.json`: name, description, skills, endpoint, auth, capabilities | `knowledge_card()`, `booking_card()` in `app/agents/*.py` |
| **Skill** | Something the agent can do, with description + examples (like a tool description, but for a whole agent) | `answer_business_question`, `manage_appointments` |
| **Message** | One turn sent to an agent; made of **parts**: text, data (JSON), files | Question text; `{"approved": true}` as a data part |
| **Task** | A unit of work with an id and a **lifecycle**: submitted → working → completed / failed / **input-required** … | Each delegation creates a task |
| **Artifact** | An output of a task; can be **streamed** in chunks | `answer` (streamed text), `sources`, `tool_call`, `tool_result` (data) |
| **Context id** | Groups related tasks/messages into one conversation | The supervisor's thread id |
| **Transport** | JSON-RPC 2.0 over HTTP, streaming via Server-Sent Events (also gRPC/REST bindings) | JSON-RPC + streaming |

### MCP vs A2A — the question you'll definitely get
| | MCP | A2A |
|---|---|---|
| Connects an agent to… | **tools** (functions with schemas) | **other agents** (autonomous peers) |
| Unit of interaction | a tool call: input → output | a **task** with a lifecycle, streaming, multi-turn |
| The other side | does exactly what it's told | reasons, plans, may ask for more input |
| VoxDesk example | `book_appointment(service_id, date, time, …)` | "Book a haircut tomorrow at 4 for Yash" |

They're complementary: **the booking agent is an A2A server for the supervisor and an MCP client
for its tools.**

**Say it like this:**
> "MCP gives an agent tools; A2A lets agents delegate to other agents. My supervisor delegates
> whole tasks over A2A — 'book this' — and the booking agent decides which MCP tools to call to do
> it. A tool returns a result; an agent can stream progress, ask for more input, and keep context
> across turns."

## 3. Why split into services at all? (and the honest trade-offs)

**Benefits**
- **Independent deployment & scaling** — the booking agent can scale or be redeployed without
  touching the API or knowledge agent; a heavy RAG load doesn't slow bookings.
- **Isolation of failure** — if the booking agent is down, knowledge questions still work, and the
  supervisor replies gracefully (tested).
- **Ownership** — in a real company, different teams own different agents; A2A is the contract.
- **Interoperability** — any A2A-compatible client (another vendor's agent, an orchestration
  platform) can use our agents via their Agent Cards. Agents can be written in any framework.
- **Least privilege** — only the booking agent holds the MCP key; only the knowledge agent needs
  embeddings.

**Costs (say these — it shows judgement)**
- **Latency:** an extra network hop per delegation (~ms locally; matters for voice).
- **Operational complexity:** more processes, more config, distributed debugging (tracing in Phase 5).
- **Consistency:** each agent has its own memory; the booking agent only sees booking turns.

> "For a single small app, one process is simpler. I split it because the specialists have
> different scaling profiles, failure modes and permissions — and because it mirrors how
> multi-agent systems are built across teams. A2A makes the boundary explicit and standard."

## 4. The server side: exposing an agent

**Files:** `app/a2a/server.py` (helpers), `app/agents/knowledge.py`, `app/agents/booking.py`

Using the official **`a2a-sdk` (v1.2)**. An agent implements one class:

```python
class KnowledgeAgentExecutor(AgentExecutor):
    async def execute(self, context: RequestContext, event_queue: EventQueue):
        task, updater = await start_task(context, event_queue)   # create/continue the task
        await updater.start_work()                               # → WORKING
        ...hybrid search...
        await emit_data(updater, "sources", [...])               # data artifact
        answer = TextStream(updater)
        async for chunk in llm.astream(...):
            await answer.write(chunk.text)                       # streamed text artifact
        await updater.complete(...)                              # → COMPLETED
```

`create_a2a_app()` mounts the JSON-RPC endpoint at `/` and the public Agent Card, and adds
**bearer-key auth** (the card stays public — discovery is the point; calling requires the key).

**Gotcha we hit while prototyping (good detail):** in this SDK version the first chunk of a streamed
artifact must *create* it (`append=False`); only later chunks may append — otherwise the server
raises `InvalidAgentResponseError`. `TextStream` encapsulates that rule. I found it by building a
throwaway echo agent first, before writing the real ones.

### The Booking Agent and human-in-the-loop over A2A
The booking graph (Phase 2) moved into the booking agent unchanged, with its **own Postgres
checkpointer** keyed by `booking:{context_id}`.

When the graph pauses with `interrupt()`, the executor maps it to A2A's native state:
```python
await updater.requires_input(updater.new_agent_message([new_data_part({"actions": [...]})]))
```
The task is now **`INPUT_REQUIRED`**. The caller replies on the **same task id** with a data part
`{"approved": true}`; the executor sees `task.status.state == INPUT_REQUIRED` and resumes the graph
with `Command(resume=...)`. The confirmation concept from Phase 2 maps 1:1 onto A2A's task lifecycle.

## 5. The client side: the supervisor

**Files:** `app/a2a/client.py`, `app/graph/supervisor.py`

`A2AAgent` resolves the Agent Card once (`/.well-known/agent-card.json`), creates an SDK client,
sends `SendMessageRequest`s and converts the streamed responses into simple events:
`task`, `token`, `data` (sources / tool_call / tool_result), `input_required`, `completed`, `failed`.

The supervisor graph:
```
route ─┬─ knowledge → delegate to Knowledge Agent ───────────────→ END
       ├─ smalltalk → respond locally ───────────────────────────→ END
       └─ booking ──→ delegate to Booking Agent ─┬─ completed ──→ END
                                                 └─ input-required → booking_confirm ⏸ (loops)
```
- **What it sends:** for knowledge, the router's **rewritten standalone question** (so the agent needs
  no conversation history); for booking, the customer's message. Plus business info as **metadata on
  every message** (A2A doesn't persist request metadata between messages — learned in the prototype).
- **Context id** = the supervisor's thread id (`business_id:thread_id`) → one A2A context per
  conversation.
- **Relaying the stream:** `delegate()` forwards each event through LangGraph's **custom stream**
  (`get_stream_writer()`); the API turns them into the same SSE events the UI already understood,
  plus a new `delegation` event (agent, task id, state).
- **Two-level human-in-the-loop:** booking agent → `input-required`; supervisor stores
  `pending_booking = {task_id, actions}` and its `booking_confirm` node calls its **own**
  `interrupt()`. The UI shows the card; `/chat/resume` resumes the supervisor, which sends
  `{"approved": …}` back on the same A2A task. Nothing before `interrupt()` has side effects, because
  LangGraph re-runs the node on resume.
- **Failure handling:** unreachable agent → a helpful fallback message; an agent's own `failed`
  message (e.g. "assistant is busy" on rate limits) is shown to the customer.

**The API contract didn't change** — the frontend still receives `token`, `sources`, `tool_call`,
`confirm` events; it just also shows which agent handled the turn.

## 6. Security

| Hop | Auth | Tenant |
|---|---|---|
| Supervisor → agents (A2A) | `Authorization: Bearer A2A_API_KEY` (constant-time check); Agent Card public | `business_id` in message metadata (trusted service-to-service) |
| Booking agent → MCP | `Authorization: Bearer MCP_API_KEY` | `X-Business-Id` header (never a tool argument) |
| Browser → API | (auth in Phase 5) | business id in request |

The Agent Card advertises the scheme (`security_schemes: {bearer: http/bearer}`) so clients know how
to authenticate. Production upgrade: OAuth 2.0 client credentials or mTLS between services, and
per-agent credentials.

## 8. Running it

```bash
cd backend
./scripts/dev_services.sh                 # MCP :8001 + Knowledge :8101 + Booking :8102 (Ctrl+C stops all)
uv run uvicorn app.main:app --reload      # API :8000 (separate terminal)
curl localhost:8101/.well-known/agent-card.json   # see an Agent Card
curl localhost:8000/health/services               # are DB, MCP and both agents reachable?
```

---

### Health checks
- `GET /health` — **liveness**: is the API process up? (cheap, no dependencies)
- `GET /health/services` — **readiness**: can the API reach Postgres, the MCP server (its public
  `/health`) and both agents (their public Agent Cards double as health probes)? Checks run **in
  parallel** with a **2 s timeout** each, so one dead service can't make the endpoint hang. Overall
  status is `ok` or `degraded`; the dashboard sidebar shows it with a per-service hover panel.

> "Liveness and readiness are separate on purpose: an orchestrator like Kubernetes restarts a
> container that fails liveness, but only stops routing traffic to one that fails readiness — a dead
> booking agent shouldn't cause the API to be restarted."

## 9. Limitations

1. **Task store is in memory** in each agent — an `input-required` task is lost if the agent
   restarts (the supervisor would get an error on resume). Fix: the SDK's `DatabaseTaskStore`.
2. Agent URLs are configured, not discovered from a registry; a real system might use an agent
   registry / catalog.
3. Shared static API key between services (production: OAuth client credentials / mTLS).
4. The booking agent only sees booking turns (its own memory), so details mentioned in a knowledge
   turn aren't visible to it.
5. Live end-to-end verification through Gemini is pending the free-tier daily quota reset (the
   protocol path is covered by the in-process A2A tests).

## Q&A

**Q: What is A2A?**
A: An open protocol for agents to discover each other via Agent Cards and collaborate on tasks over
HTTP (JSON-RPC), with streaming, multi-turn tasks and states like input-required.

**Q: MCP vs A2A?**
A: MCP connects an agent to tools; A2A connects agents to agents. In VoxDesk the booking agent is
an A2A server to the supervisor and an MCP client to its booking tools.

**Q: What's in an Agent Card?**
A: Name, description, version, endpoint URL and protocol binding, capabilities (e.g. streaming),
skills with descriptions/examples, input/output modes, and security schemes.

**Q: How does human confirmation work across agents?**
A: The booking agent's graph interrupts, so its A2A task goes to `input-required` with the action
details. The supervisor stores the pending task and interrupts its own graph; the UI asks the
customer; the resume endpoint continues the supervisor, which replies on the same A2A task with
`{"approved": true}`, and the booking agent resumes its graph.

**Q: How do you stream a remote agent's answer to the browser?**
A: The agent streams artifact chunks over A2A (SSE); the supervisor's delegate step forwards each
chunk through LangGraph's custom stream; the API emits them as SSE tokens to the browser.

**Q: What if an agent is down?**
A: The supervisor catches it and answers with a helpful fallback; other agents keep working.
Production would add retries with backoff, circuit breakers and health checks.

**Q: Does multi-agent mean every agent runs on its own server?**
A: No. Multi-agent is a design pattern; most systems run all agents in one process (e.g. LangGraph
nodes/subgraphs). Separate services are a deployment choice for team ownership, scaling, security or
interoperability. VoxDesk has both: an in-process tool-using booking agent, and specialists
delegated to over A2A.

**Q: Why not just call the agents as Python functions?**
A: That's simpler for one team and one process. Separate A2A services buy independent scaling and
deployment, failure isolation, least-privilege credentials, and interoperability — at the cost of
latency and operational complexity.
